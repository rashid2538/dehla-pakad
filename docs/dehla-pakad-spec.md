# Dehla Pakad — Multiplayer Game Design & Technical Specification

**Version:** 1.0
**Stack:** Flutter (client) + Firebase (backend)
**Scope:** 4-player, 2-team, real-time multiplayer implementation
**Status:** Implementation-ready

---

## 0. How to Read This Document

This specification resolves every ambiguity in the original rule draft, states the assumptions made, and defines a server-authoritative architecture so that no gameplay decision is left to the developer's discretion during implementation. Wherever the source draft conflicted with standard Dehla Pakad play, the conflict is called out explicitly in a **⚠ Resolution** box, with the reasoning and the final ruling.

Standard Dehla Pakad (also called "Dehla Pakad," "Get Away," or in some regions "Tens" / "Bhabhi-adjacent trick games") is a regional Indian trick-taking game with many local variants. Because local variants disagree on details (especially trump declaration and the *"Court"/"Poopy"* terminology), this spec treats your draft as the **canonical house-rule set** and formalizes it rather than overriding it with a different regional variant. Every ruling below is internally consistent and deterministic.

## 1. Terminology

| Term | Definition |
|---|---|
| **Trick** | One round in which each of the 4 players plays exactly one card (4 cards total). |
| **Lead suit** | The suit of the first card played in a trick. |
| **Trump suit** | A single suit, established once per game, whose cards outrank all non-trump cards regardless of the lead suit. |
| **Trump-setting team** | The team of the player whose card *establishes* the trump suit (see §7, §11-A). |
| **Ten-holder team** | The team that has collected all four 10s in its trick pile at any given moment (may be neither team, or may change hands as tricks are won). |
| **Dehla** | Hindi/Punjabi colloquial term for the "10" card — the objective card of the game. |
| **Court Victory** | The ten-holder team is *also* the trump-setting team. *(Custom/house terminology — see §10 note.)* |
| **Poopy Victory** | The ten-holder team is *different from* the trump-setting team. *(Custom/house terminology — see §10 note.)* |
| **Void in a suit** | A player holds zero cards of that suit. |
| **Renege / Reneging** | Illegally failing to follow suit when able to — must be prevented by server-side validation, not merely discouraged. |

> **⚠ Terminology note (ref. §10):** "Court Victory" and "Poopy Victory" are **not** standard published Dehla Pakad terms — they don't appear in the common written rule sets for this game family (which usually just distinguish a plain win from a win where the winning team never got to set trump). They read as **house/local slang**, plausibly regional to your play-group. This spec preserves them exactly as given and treats them as custom terminology, formalized in §10.

## 2. Game Overview

- **Players:** Exactly 4 (fixed for v1 — no 6-player "Double Dehla Pakad" variant, no bot fill-in).
- **Teams:** 2 teams of 2, fixed by **seating position**, not by player choice of teammate.
  - Team A = Seat 1 + Seat 3
  - Team B = Seat 2 + Seat 4
- **Deck:** Standard 52-card deck, no jokers.
- **Deal:** 13 cards per player, entire deck distributed (no kitty/widow).
- **Objective:** Be the team that ends the game holding all four 10s in your collected tricks.
- **Game length:** Up to 13 tricks, but can end early (§9, §11-H).

## 3. Room / Lobby System

### 3.1 Create Room

- Any authenticated user can create a room and becomes **Host**.
- Host chooses a **room code**.
  - **Assumption:** Room codes are short (6 characters), alphanumeric, uppercase, auto-generated by default, with an *optional* custom code the host may type instead (subject to a uniqueness check against currently-active rooms). This satisfies "preferably customizable" without allowing collisions.
  - Custom codes are validated server-side (Cloud Function) for: length (4–10 chars), allowed characters (`A–Z`, `0–9`), profanity filter, and current availability (no other **active** room may hold the same code — codes recycle once a room is closed/archived).
- Host sees a live list of joined players and their seat assignment as they arrive.
- **Start Game** button is enabled only when exactly 4 players occupy 4 distinct seats and all 4 have signaled "ready" (see §3.4).

### 3.2 Join Room

| Scenario | Resolution |
|---|---|
| Code does not exist | Client shows "Room not found." No Firestore write occurs; this is a read-only lookup, so no security concern. |
| Room is full (4/4) | Join is rejected with "Room is full." **Exception:** if the joining user's ID already occupies a seat in that room (e.g., app was killed and relaunched), they are **reconnected** to their existing seat instead of being treated as a 5th player. |
| Room's game already `IN_PROGRESS` | New (never-seen-before) users cannot join — "Game already in progress." A returning player (matching `userId`) is reconnected instead (§3.6). |
| Player leaves before game starts | Allowed freely. Their seat becomes empty; other waiting players are notified in real time. |
| Host removes a player | Allowed **only pre-game** (`status == LOBBY`). Host taps a "kick" affordance next to a seated player; a Cloud Function validates the requester is the current host, then vacates that seat. Cannot be used mid-game — see disconnect handling instead. |
| Host disconnects (pre-game) | Room remains open. A grace period (**Assumption:** 60 seconds) is given; if the host doesn't reconnect, host role transfers automatically to the next-longest-seated player (§3.3). |
| Host disconnects (mid-game) | Host status is purely a lobby/administrative role by this point — see §3.6. Game continues to be server-driven regardless of who is "host." |
| Player disconnects mid-game | See §3.6 (Reconnection). Game does **not** immediately end; a reconnect window is provided, then a forfeiture/pause policy applies. |

### 3.3 Host Transfer

- Host is just a flag on one `players[]` entry (`isHost: true`), not a special runtime role beyond lobby administration (starting the game, kicking pre-game, configuring room settings).
- Transfer triggers: explicit host-initiated "make host" action, OR automatic transfer after the host-disconnect grace period.
- Automatic transfer order: seat order starting from Seat 1, skipping any currently-disconnected players.

### 3.4 Ready Check

- **Assumption (new, filling a gap in the draft):** Each seated player must mark themselves "Ready." This avoids the host starting a game before a player has finished, e.g., setting a display name/avatar, and gives a clean "all 4 present AND all 4 ready" gate for the Start button — otherwise "exactly 4 players present" alone is ambiguous about players who joined but are still mid-setup (e.g. mid-reconnect).

## 4. Seating & Teams

- 4 fixed seats: **North (1), East (2), South (3), West (4)** — mapped to Player 1–4 in the original draft.
- Teams are **derived from seat**, not chosen:
  - Team A: North + South (Seats 1 & 3)
  - Team B: East + West (Seats 2 & 4)
- **Seat selection:** Players may pick any open seat in the lobby (first-come, first-served, no locking mechanism needed beyond a Firestore transaction on the seat-claim field, to prevent two clients claiming the same seat in a race).
- Once the game starts, seats are frozen for the duration of that game.
- **Assumption:** The host may optionally **shuffle/randomize seats** with one tap before starting, for players who don't care who partners whom — but this is a lobby-only convenience feature, not a required rule.

## 5. Deck & Dealing

### 5.1 Card Set

- 4 suits × 13 ranks = 52 cards, no jokers.
- Rank order within a suit (high→low): `A, K, Q, J, 10, 9, 8, 7, 6, 5, 4, 3, 2`.

### 5.2 Dealing Algorithm (server-authoritative, runs in a Cloud Function)

```text
1. Build canonical 52-card array: [ "AS","KS", ... "2C" ] (suit-major or rank-major, doesn't matter).
2. Cryptographically shuffle using a secure RNG
   (Node crypto.randomInt / Fisher–Yates with a CSPRNG seed — never Math.random()).
3. Deal round-robin, 1 card at a time, starting from the (randomly chosen) starting player,
   proceeding in seat order, until each of the 4 players has 13 cards.
4. Persist each player's 13-card hand to a PRIVATE, per-player-readable-only subcollection
   (see §13.2) — never to a document any other client can read.
5. Zero cards remain undealt; there is no kitty.
```

- **Why round-robin dealing from the starting player, not a single 13-card slice:** This mirrors physical dealing and has no functional effect on fairness given a CSPRNG shuffle, but it's specified precisely so there's exactly one implementation, not developer choice.
- Dealing must happen **entirely server-side** (Cloud Function triggered by `status: LOBBY → DEALING`). No client ever sees the pre-deal shuffled deck.

### 5.3 Storing Deal State Without Leaking Hands

See §13.2 for the exact Firestore layout. In short: each player's hand lives in a document only that player's UID can read, enforced by Firestore Security Rules — never by client-side omission (a malicious client could otherwise just listen to the collection).

## 6. Starting Player & Turn Order

- The starting player for **trick 1 only** is chosen **randomly by the server** (Cloud Function, same CSPRNG as the shuffle) — never client-selected, never "Player 1 always starts," to prevent any perceived or actual seat-based advantage.
- Turn order proceeds **clockwise in seat order** (Seat 1 → 2 → 3 → 4 → 1 → …) — standard for trick-taking games, and implied but not explicitly stated in the draft. **Assumption confirmed:** turn order is fixed seat rotation, not "next available player" or any dynamic ordering.
- After a trick resolves, **the trick's winner leads the next trick** (draft's own rule, retained as-is) — this can break strict seat rotation, which is expected and correct for this genre (the winner "gets the lead").

## 7. Trick Rules

### 7.1 Leading a Trick

- The player on lead may play **any card** from their hand — no restriction, even after trump is established. (Leading trump is always legal.)
- The suit of the led card becomes that trick's **lead suit** (reset every trick; distinct from the game-long trump suit).

### 7.2 Following Suit

```text
IF player holds ≥1 card of the lead suit:
    → player MUST play a card of the lead suit (mandatory follow)
ELSE (player is void in the lead suit):
    → player may legally play ANY card in hand:
        - a card of the (already-established) trump suit, OR
        - a card of any other off-suit, OR
        - if trump is not yet established, any card at all — and per §7.3,
          the FIRST such off-suit card in the game establishes trump.
```

- This must be enforced **server-side** at card-play time (§16), not just suggested in the UI — a malicious/modified client must not be able to submit an illegal card.

### 7.3 Trump-Establishment Timing — Resolving §11-D

**⚠ Resolution (ref. §7, §11-D):** The draft states trump is established "when a player cannot follow suit and plays a card of another suit," but does not say *when* — at the moment the card is played, or only after the trick resolves. Standard Dehla Pakad practice (and the only version that is internally consistent with §7's card-legality rule) is:

> **Trump is established the instant the off-suit card is placed on the table — not retroactively, and not only after the trick completes.**

This matters concretely: if Player C (void in lead suit) plays a Spade to establish trump as Spades, and Player D (the 4th to act, also void in lead suit) then plays, Player D is now bound by the *already-active* trump suit — Player D may choose to also throw trump, or throw any other off-suit card, but Spades is trump **for Player D's decision too**, since it was set by C's play a moment earlier in the same trick. Establishing trump only "after the trick" would create a paradox: you can't know whether the 3rd or 4th player's play *was itself* trump-establishing without already knowing the trump suit.

### 7.4 §11-B — Can a Void Player Choose *Not* to Play Trump?

**⚠ Resolution:** Yes. A player who is void in the lead suit is **never obligated to play trump**, whether or not trump has already been established. They may discard any off-suit, non-trump card ("sloughing") purely at their discretion. This is standard trick-taking-game behavior and is the only reading of the draft consistent with §7's "may play any card" language. The *only* mandatory action in the entire game is following the lead suit when able.

### 7.5 §11-C — Trump Availability After Establishment

**⚠ Resolution:** Once established, the trump suit is simply **always "live"** for the rest of the game — there is no additional gating condition (e.g., no "trump must be broken by X" rule as in some Western trick games like Spades). From the moment it's set, any player who is void in the current trick's lead suit may play a trump card on that very trick, immediately, with no waiting period. This keeps the rule set minimal and matches the draft's intent ("It remains fixed for the entire game").

### 7.6 §11-E / §11-F — Can Trick 1 Establish Trump? Can the Leader Establish It?

- **§11-E — Yes.** Trick 1 is not special-cased. If any of players 2, 3, or 4 in trick 1 is void in the lead suit and plays an off-suit card, trump is established immediately, exactly as in any later trick.
- **§11-F — Confirmed, with one clarification.** The player who **leads** a trick chooses the lead suit and therefore, *by definition*, cannot simultaneously be void in it — so the leader can never be the one to establish trump **on their own lead**. However, note this is a per-trick statement, not "the very first player of the game can never establish trump" — if that same player is void in a later trick's lead suit (set by someone else), they can absolutely be the one who sets trump at that point. The draft's phrasing ("the first player") is ambiguous between "first player of trick 1" and "whoever leads any trick" — this spec confirms it means **the leader of the current trick, every trick**, which is the only version consistent with the rest of the ruleset.

## 8. Determining the Trick Winner

### 8.1 Algorithm

```text
FUNCTION resolveTrick(playedCards[4], leadSuit, trumpSuit):
    trumpCardsPlayed = filter(playedCards, card => card.suit == trumpSuit)

    IF trumpCardsPlayed is NOT empty:
        winner = highest-rank card within trumpCardsPlayed
    ELSE:
        leadSuitCards = filter(playedCards, card => card.suit == leadSuit)
        winner = highest-rank card within leadSuitCards
        // Off-suit, non-trump cards can NEVER win a trick, regardless of rank.

    RETURN winner.player
```

- **§11-G — Multiple trump cards in one trick:** Fully covered by the algorithm above — filter to trump cards, take the highest rank among *only* those. Off-suit non-trump "slough" cards are irrelevant to winner determination even if, e.g., an Ace of an off-suit was played — an off-suit Ace never beats anything once any trump is on the table, and never beats the lead suit either (it only matters if it happens to *be* the lead suit).
- **Edge case — trump suit not yet established at all in this trick, and this trick's lead suit is not fully followed:** If trump has never been established in the game and every void player in this trick throws various off-suit cards (none of which is *the first* off-suit throw — only the very first such play in the whole game sets trump, all subsequent off-suit throws before that first moment are moot because trump gets set on that first occurrence) — practically, this resolves to: the moment the *first* off-suit card of the entire game is played, trump is set from that instant onward, so by the time trick resolution runs, trump is already known (either "still unset, because this trick never produced an off-suit play" or "set as of card N of this trick"). Case 1 (§8, "no trump card played") applies whenever this trick contains zero cards of the (possibly still-unset) trump suit — which trivially includes the case where trump has never been set at all yet.

### 8.2 Trick Completion

1. Server determines winner via §8.1.
2. The 4 cards are appended to the **winning team's** (not just winning player's) collected-cards pile.
3. `collectedTens` map is updated if any of the 4 cards was a 10 (§9).
4. Victory check runs (§9, §11-H).
5. If no victory, winner becomes next trick's leader; `trickNumber` increments; `currentTrick` resets to empty.

## 9. Collecting the Four 10s

- Server maintains a live map, e.g.:
  ```json
  "collectedTens": {
    "10S": "teamA",
    "10H": "teamA",
    "10D": null,
    "10C": "teamB"
  }
  ```
- Updated at the end of every trick resolution (§8.2), by checking each of the 4 played cards against the 4 ten-identifiers.
- **§11-H — Immediate end vs. finish the trick:** The draft explicitly states a preference for immediate termination "once ownership... has been conclusively determined." This spec adopts that, with one necessary precision:

  > **A team wins the instant all four `collectedTens` values point to that same team — checked immediately after each trick's cards are added to a pile, not mid-trick.** Since a 10 can only ever be collected as one of the 4 cards *of a completed trick*, there is no such thing as "mid-trick" ownership anyway — a 10 is either still in some player's hand (unresolved) or already in a completed trick's pile (resolved). So "immediate" here concretely means: **the moment the 4th trick-completing 10 lands in a team's pile, that trick is still allowed to fully resolve (all 4 cards assigned, since resolution is atomic — see §8.2, §17), and the game ends immediately after, without dealing out or playing any further tricks**, even if tricks remain (e.g., victory could occur as early as trick 4, if a team happens to win 4 tricks that collectively contain all four 10s).

- This also means: a team can hold 3 of the 4 tens for most of the game and still lose if the 4th ten ends up in a trick the other team wins — ownership is **not cumulative-across-attempts**, it's simply "whoever's pile that specific ten card is sitting in right now." A ten is never "lost" once collected — teams don't hold the *same* ten card twice; each of the 4 physical ten-cards belongs to exactly one team once its trick is resolved, permanently, for the rest of that game.

## 10. Victory Conditions

Two victory *types*, gated on **(a)** which team holds all 4 tens, and **(b)** which team established trump (§7.3, §11-A):

| Ten-holder team | Trump-setting team | Result |
|---|---|---|
| Team A | Team A | **Court Victory** for Team A |
| Team B | Team B | **Court Victory** for Team B |
| Team A | Team B | **Poopy Victory** for Team A |
| Team B | Team A | **Poopy Victory** for Team B |

- **Edge case — trump never established at all:** It's possible for a game to end (or even complete all 13 tricks) without *any* player ever having been void in a lead suit — meaning trump is never set. In that case, `trumpTeam` is `null`.
  - **Ruling:** If a team collects all four 10s while `trumpTeam == null`, the result is still a **Poopy Victory** by default, since the ten-holding team by definition is *not* "the team that set trump" (nobody did). This is the simplest, most deterministic rule and avoids inventing a third victory category not present in the draft.
- **Edge case — nobody collects all four 10s after 13 tricks:** All 13 tricks complete, hands are exhausted, and the 10s are split between the two teams (e.g., 3–1 or 2–2).
  - **Assumption (gap in the draft — must be resolved for a deterministic implementation):** Declare the result a **Draw / No Ten-Sweep**, and record the actual 10 split (e.g., "Team A: 3 tens, Team B: 1 ten") for display and history purposes. The draft does not define a fallback scoring rule (such as "most tricks wins" or "most tens wins if no team gets all four") — rather than inventing a house-point system unprompted, this spec surfaces the split neutrally as a draw outcome. **If your play-group has a tie-break convention (e.g., "most tens wins outright even without all 4"), that should be layered on top of this spec explicitly — flagging it here rather than guessing.**

## 11. Rule Clarification Summary (§11 A–H, consolidated)

| # | Question | Ruling | Reference |
|---|---|---|---|
| A | What determines the trump-setting team? | The team of the player whose card is the very first off-suit (non-lead-suit) card played in the entire game. | §7.3 |
| B | Can a void player avoid playing trump? | Yes, always — no obligation to trump in, ever. | §7.4 |
| C | Extra restrictions on trump once set? | None — trump is unconditionally live from the instant it's established. | §7.5 |
| D | Trump active immediately or after trick ends? | Immediately, at the moment the card is placed. | §7.3 |
| E | Can trick 1 establish trump? | Yes. | §7.6 |
| F | Can the leader establish trump? | No — never on their own lead, for any trick (they can't be void in a suit they themselves chose). | §7.6 |
| G | Multiple trump plays in one trick? | Highest-ranked trump among those played wins, full stop. | §8.1 |
| H | Game ends immediately on 4th ten? | Yes — after the current trick fully resolves (atomically), no further tricks are dealt. | §9 |

## 12. Multiplayer Architecture — Server-Authoritative Design

### 12.1 Principle

**The Flutter client is a dumb terminal for input and rendering.** It never computes shuffles, deals, turn order, trick winners, trump state, ten-ownership, or victory. It only:
1. Renders whatever state Firestore gives it (scoped to what that player is allowed to see).
2. Sends a single, minimal "intent" (e.g., `playCard(cardId)`) to a Cloud Function.
3. Reacts to the resulting state change via a Firestore listener.

### 12.2 Recommended Firebase Products

| Product | Use | Why |
|---|---|---|
| **Firebase Authentication** | Anonymous auth (fast onboarding) upgradeable to Google/email sign-in for persistent stats/history. | Every action must be tied to a verifiable UID for security rules and Cloud Function validation. |
| **Cloud Firestore** | Primary game state store: rooms, players, hands, tricks, history. | Structured document/subcollection model fits nested per-player-private data well; native security rules; real-time listeners for reactive UI. |
| **Cloud Functions (2nd gen, callable + Firestore triggers)** | All authoritative logic: room creation, dealing, card-play validation, trick resolution, victory checks, disconnect/reconnect handling, host transfer. | This is *the* server-authoritative layer — the only place allowed to write to sensitive fields. |
| **Realtime Database (optional, presence only)** | Player online/offline presence via RTDB's native `onDisconnect()` hook. | Firestore has no built-in "disconnect" detection; RTDB's presence pattern is the standard, well-documented solution for this specific problem. Everything else stays in Firestore. |
| **Cloud Messaging (optional, v2+)** | Push notification "It's your turn" / "Your opponent reconnected" when app is backgrounded. | Nice-to-have for engagement, not required for v1 correctness. |

**Recommendation:** Firestore + Cloud Functions is the backbone. Add RTDB **only** for the presence sub-system (its `onDisconnect()` primitive has no clean Firestore equivalent). Skip FCM for v1; add it once core gameplay is stable.

### 12.3 Why Not Realtime Database for Everything

Firestore's structured collections/subcollections + native per-document security rules map far more cleanly onto "player A can read player A's hand but not player B's" than RTDB's flatter JSON tree, where equivalent security rules are harder to express and audit. Firestore is the better fit for the bulk of this game's state.

## 13. Firestore Data Model

### 13.1 Top-Level Structure

```text
/games/{gameId}
    status: "LOBBY" | "DEALING" | "IN_PROGRESS" | "PAUSED" | "COMPLETED" | "ABANDONED"
    roomCode: string
    hostId: uid
    createdAt: timestamp
    startedAt: timestamp | null
    seats: {                      // seat -> player mapping
      "1": { uid, displayName, connected: bool, ready: bool },
      "2": { ... },
      "3": { ... },
      "4": { ... }
    }
    teams: {
      teamA: { seats: [1, 3] },
      teamB: { seats: [2, 4] }
    }
    startingPlayerSeat: 1-4 | null
    currentTurnSeat: 1-4 | null
    leadSuit: "S"|"H"|"D"|"C" | null      // resets each trick
    trumpSuit: "S"|"H"|"D"|"C" | null     // set once, permanent
    trumpTeam: "teamA" | "teamB" | null
    trickNumber: 1-13
    currentTrick: {
      leaderSeat: 1-4,
      plays: [ { seat, card, playedAt }, ... ]   // 0-4 entries, in play order
    }
    collectedTens: { "10S": teamId|null, "10H": ..., "10D": ..., "10C": ... }
    trickPiles: {
      teamA: { trickCount: n, cards: [...] },   // cards optional if only count matters for scoring
      teamB: { trickCount: n, cards: [...] }
    }
    winningTeam: "teamA" | "teamB" | null
    victoryType: "COURT" | "POOPY" | "DRAW" | null
    updatedAt: timestamp

/games/{gameId}/privateHands/{uid}          // ⚠ security-critical subcollection, see §13.2
    cards: ["AS", "KH", ... ]                // exactly this player's remaining hand

/games/{gameId}/history/{eventId}            // append-only event log, see §18
    type: "CARD_PLAYED" | "TRICK_RESOLVED" | "TRUMP_SET" | "TEN_COLLECTED" | "GAME_ENDED" | ...
    payload: { ... }
    createdAt: timestamp
    sequence: number                          // monotonic, for ordered replay
```

### 13.2 Protecting Private Hands

- `privateHands/{uid}` is a **subcollection keyed by UID**, so Security Rules can do a direct, cheap ownership check:

```javascript
// Firestore Security Rules (illustrative)
match /games/{gameId}/privateHands/{uid} {
  allow read: if request.auth != null && request.auth.uid == uid;
  allow write: if false; // ONLY Cloud Functions (Admin SDK) may write hands, ever.
}

match /games/{gameId} {
  allow read: if request.auth != null && isPlayerInGame(gameId, request.auth.uid);
  allow write: if false; // ALL game-state mutation goes through Cloud Functions.
}

match /games/{gameId}/history/{eventId} {
  allow read: if request.auth != null && isPlayerInGame(gameId, request.auth.uid);
  allow write: if false;
}
```

- **Absolute rule: no client ever has direct write access to `/games/{gameId}` or any subcollection.** Every mutation — creating a room, joining, marking ready, playing a card, everything — goes through a **callable Cloud Function**, which uses the Admin SDK (which bypasses security rules by design) to perform the actual write after validating the request server-side. This single choice is what makes the "clients cannot manipulate game state" requirement (§13, §17) actually enforceable, rather than aspirational.
- Clients never even attempt direct Firestore writes to game documents — the SDK calls are all `httpsCallable('playCard', {...})`-style RPCs.

## 14. Cloud Function Responsibilities

| Function | Trigger | Responsibility |
|---|---|---|
| `createRoom` | Callable | Validates/generates room code, creates `/games/{gameId}`, seats host, sets `status: LOBBY`. |
| `joinRoom` | Callable | Validates room exists, not full, seats player (transactional seat claim), or reconnects existing UID. |
| `leaveRoom` / `kickPlayer` | Callable | Pre-game only; vacates a seat; handles host-transfer if the host leaves. |
| `setReady` | Callable | Toggles a seated player's ready flag. |
| `startGame` | Callable | Validates caller is host, 4/4 seated & ready; triggers `dealCards`; transitions `LOBBY → DEALING`. |
| `dealCards` | Internal (invoked by `startGame`, or a Firestore trigger on the status change) | Runs §5.2 shuffle/deal; writes 4 `privateHands` docs; picks random starting player (§6); transitions `DEALING → IN_PROGRESS`. |
| `playCard` | Callable | **The core validator** — runs the full pseudocode in §16; on success, mutates `currentTrick`, removes the card from `privateHands`, advances `currentTurnSeat`, and — if this was the trick's 4th card — invokes `resolveTrick`. |
| `resolveTrick` | Internal (invoked by `playCard` on the 4th play, inside the same transaction) | Runs §8.1 algorithm; updates `trickPiles`, `collectedTens`, checks §9/§11-H victory condition; either ends the game (§10) or resets `currentTrick`/increments `trickNumber` and sets the new leader. |
| `handleDisconnect` / `handleReconnect` | RTDB `onDisconnect` webhook via Cloud Function, or Firestore-triggered from presence writes | Marks a seat `connected: false` / `true`; manages the pause/forfeit policy (§17.5). |
| `abandonGame` | Scheduled/Callable | Cleans up rooms stuck in `LOBBY` for too long, or games where all 4 players have been disconnected past a grace threshold. |

All of the above (except pure lobby actions) run inside **Firestore transactions** to guarantee atomicity — critical for `playCard`/`resolveTrick`, discussed in §17.

## 15. Game State Machine

### 15.1 States

```text
LOBBY
DEALING
IN_PROGRESS
  ├── (sub-state, informational only) AWAITING_PLAY   — waiting on currentTurnSeat
  └── (sub-state, informational only) RESOLVING_TRICK  — transient, inside a transaction
PAUSED
COMPLETED
ABANDONED
```

> **Note:** `AWAITING_PLAY` and `RESOLVING_TRICK` are not separately persisted top-level `status` values — they are *derived* client-side from `currentTrick.plays.length` (0–3 = awaiting a play; the 4th play triggers resolution synchronously inside the same Cloud Function transaction, so there's no observable "resolving" window from the client's perspective — it's atomic). This keeps the actual `status` enum small and every value meaningfully distinct.

### 15.2 Transitions

| From | To | Trigger | Who/What |
|---|---|---|---|
| — | `LOBBY` | Room created | `createRoom` (any authenticated user) |
| `LOBBY` | `DEALING` | Host starts game, 4/4 ready | `startGame` (host only) |
| `DEALING` | `IN_PROGRESS` | Deal completes | `dealCards` (system, automatic) |
| `IN_PROGRESS` | `IN_PROGRESS` | Card played, trick doesn't end game | `playCard` → `resolveTrick` |
| `IN_PROGRESS` | `PAUSED` | A player disconnects past grace period | `handleDisconnect` (system) |
| `PAUSED` | `IN_PROGRESS` | Disconnected player reconnects within policy window | `handleReconnect` (system) |
| `IN_PROGRESS` | `COMPLETED` | Victory condition met (§9/§10) or 13th trick resolves in a draw | `resolveTrick` (system) |
| `PAUSED` | `ABANDONED` | Disconnected player never returns past a longer timeout | `abandonGame` (scheduled) |
| `LOBBY` | `ABANDONED` | Room sits empty/inactive past a timeout | `abandonGame` (scheduled) |

### 15.3 Invalid Transitions

Anything not listed above is rejected — e.g., `LOBBY → IN_PROGRESS` directly (must pass through `DEALING`), or any transition triggered by a non-host/non-system caller. Every Cloud Function begins by asserting `status` is one of its expected pre-states before doing anything else; a stale/duplicate client call that arrives after the state has already moved on is a no-op (idempotency, §17.2).

### 15.4 Recovery After Disconnects

Covered fully in §17.5 — summarized here: `PAUSED` freezes `currentTurnSeat` (no timer runs against the disconnected player) and simply waits; on reconnect, the client re-subscribes to the same `gameId` and instantly resumes from whatever state is in Firestore (there is nothing to "recover" server-side, since Firestore already holds the single source of truth continuously).

## 16. Turn/Card-Play Validation

### 16.1 Full Validation Pseudocode (`playCard` Cloud Function)

```text
FUNCTION playCard(uid, gameId, cardId):
    TRANSACTION:
        game = get(/games/{gameId})

        // 1. Game state checks
        IF game.status != "IN_PROGRESS":
            REJECT "Game is not active"

        // 2. Turn check
        callerSeat = seatOf(game, uid)
        IF callerSeat == null:
            REJECT "You are not a player in this game"
        IF game.currentTurnSeat != callerSeat:
            REJECT "It is not your turn"

        // 3. Ownership check
        hand = get(/games/{gameId}/privateHands/{uid})
        IF cardId NOT IN hand.cards:
            REJECT "You do not hold this card"
            // (Also implicitly prevents playing an already-played/duplicate card,
            //  since a played card is removed from the hand at play time.)

        // 4. Follow-suit legality check
        leadSuit = game.currentTrick.plays.isEmpty
                     ? null                          // this play WILL set the lead suit
                     : game.leadSuit
        IF leadSuit != null:
            playerHasLeadSuit = ANY(hand.cards, c => c.suit == leadSuit)
            IF playerHasLeadSuit AND card(cardId).suit != leadSuit:
                REJECT "You must follow suit"
            // else: void in lead suit (or this is the opening lead) → any card is legal

        // 5. Trick-already-complete / game-already-ended guards
        IF game.currentTrick.plays.length >= 4:
            REJECT "Trick already complete"   // defensive; should be unreachable given §17 atomicity
        IF game.winningTeam != null:
            REJECT "Game already ended"        // defensive; should be unreachable given status check above

        // --- All checks passed: commit the play ---
        remove cardId from hand.cards
        append { seat: callerSeat, card: cardId, playedAt: now() } to game.currentTrick.plays

        IF game.trumpSuit == null AND leadSuit != null AND card(cardId).suit != leadSuit:
            game.trumpSuit = card(cardId).suit
            game.trumpTeam = teamOf(callerSeat)
            logEvent("TRUMP_SET", { suit: game.trumpSuit, team: game.trumpTeam, byPlayer: uid })

        IF game.currentTrick.plays.length == 1:
            game.leadSuit = card(cardId).suit   // this play's suit becomes the trick's lead suit

        logEvent("CARD_PLAYED", { uid, cardId, seat: callerSeat })

        IF game.currentTrick.plays.length == 4:
            resolveTrick(game)     // §8.1 — runs INSIDE this same transaction
        ELSE:
            game.currentTurnSeat = nextSeat(callerSeat)

        COMMIT
```

### 16.2 Why This Must Be a Single Transaction

Steps 1–5 (validate) and the subsequent writes (commit) must be atomic — otherwise two near-simultaneous calls could both pass validation against a stale read before either commits (a classic check-then-act race). Firestore transactions handle this natively via optimistic concurrency: if the transaction's read set changes before commit, it automatically retries.

## 17. Concurrency & Cheating Prevention

| Threat | Mitigation |
|---|---|
| Two clients play "simultaneously" (e.g., a bug lets a player double-tap, or two devices logged into the same account) | Firestore transaction on `playCard` — the loser of the race sees `currentTurnSeat` has already advanced (or the hand no longer contains the card) on retry and is rejected. Only one write wins. |
| Duplicate card-play requests (e.g., client retries a call after a flaky network response) | Idempotency: once a card is removed from `privateHands`, a duplicate request for the same `cardId` fails the ownership check (step 3, §16.1) — naturally idempotent without needing a separate request-ID ledger, though adding one (a `lastRequestId` per player, checked and stored) is a reasonable defensive addition for exactly-once semantics on flaky mobile networks. |
| Network latency / stale UI | Client always renders from the live Firestore listener, never from optimistic local state for anything security-relevant (it *may* optimistically grey out a card the instant it's tapped, purely cosmetic, but the authoritative state always wins on listener update — including rolling back a rejected optimistic UI change). |
| Player reconnects mid-game | §17.5 / §3.6 — client re-subscribes; no special server action needed since Firestore is already the source of truth. |
| Player closes the app | RTDB `onDisconnect()` flips `connected: false`; §17.5 pause policy engages. |
| Stale clients (old app version, or a client that's been backgrounded a long time) | Every callable Function re-validates full game state fresh on every call (§16.1) — a stale client's *belief* about the state is irrelevant; only what it submits (a single `cardId`) matters, and that's checked against live server state. |
| Manipulated/forged Firebase requests (e.g., someone calling `playCard` with someone else's seat) | `request.auth.uid` on a Cloud Functions callable is populated by Firebase's verified ID token — **not** client-supplied — so `seatOf(game, uid)` can never be spoofed to act as another player. |
| Replay/duplicate actions | Same idempotency mechanism as duplicate requests above; additionally, `history` events carry a monotonic `sequence` number so any replay tooling can detect/ignore duplicates. |
| Race conditions resolving a trick | `resolveTrick` runs *inside* the same transaction as the 4th `playCard` call (§16.1) — there is no separate "resolve" step that could race against a 5th erroneous play, because step 1's status/trick-length guards make a 5th play on an already-4-card trick structurally impossible to submit before the transaction that closes it out commits. |
| Client tampering with local Firestore cache to fake a bigger hand, etc. | Irrelevant — the client never authors game-state documents at all (§13.2); it can only read. Rendering garbage locally doesn't affect the authoritative state other players and the server see. |

## 18. Game History & Replay Model

**Recommendation: yes, record everything**, via the append-only `/games/{gameId}/history/{eventId}` subcollection introduced in §13.1. This is cheap (Firestore writes are already happening for each play) and unlocks replay, stats, and leaderboards without any redesign later.

### 18.1 Event Types

```json
{ "type": "GAME_STARTED", "sequence": 0, "payload": { "startingSeat": 3 } }
{ "type": "CARD_PLAYED", "sequence": 1, "payload": { "seat": 3, "card": "7H" } }
{ "type": "TRUMP_SET", "sequence": 4, "payload": { "suit": "S", "team": "teamB", "byPlayer": "uid_..." } }
{ "type": "TRICK_RESOLVED", "sequence": 5, "payload": { "trickNumber": 1, "winnerSeat": 2, "winningCard": "5S", "cards": ["7H","KH","5S","3H"] } }
{ "type": "TEN_COLLECTED", "sequence": 9, "payload": { "card": "10H", "team": "teamA", "trickNumber": 2 } }
{ "type": "GAME_ENDED", "sequence": 52, "payload": { "winningTeam": "teamA", "victoryType": "POOPY", "finalTens": {...} } }
```

### 18.2 What This Enables Later

- **Replay:** Full deterministic reconstruction — replay a game trick-by-trick in the UI by simply iterating `history` in `sequence` order.
- **Match history:** Query `history` where `payload.uid == currentUser` across `games` (would need a lightweight `/userGames/{uid}/{gameId}` index doc for efficient lookup, since Firestore can't easily query "games this user played" from the `games` collection alone at scale).
- **Player statistics:** Aggregate wins/losses, Court vs. Poopy win rate, average tricks-to-win, favorite trump suit set, etc. — best computed by a scheduled Cloud Function that rolls up completed games into a `/userStats/{uid}` summary doc, rather than recomputing from raw history on every profile view.
- **Leaderboards:** A denormalized `/leaderboard/{uid}` collection (win count, win rate) updated incrementally by the same `GAME_ENDED` handler, queried with a simple `orderBy`.

## 19. Flutter Application Architecture

### 19.1 State Management Recommendation: **Riverpod**

**Chosen over Bloc and plain Provider for this project specifically because:**
- The app is fundamentally **one continuously-streamed Firestore document** (`/games/{gameId}`) plus one private subcollection (`privateHands/{uid}`) driving almost the entire UI — Riverpod's `StreamProvider`/`AsyncNotifierProvider` maps onto "subscribe to a Firestore stream, expose typed state, rebuild dependents" with very little boilerplate, and its dependency graph (`ref.watch`) makes deriving things like "is it my turn," "can I legally play this card," and "which suit is trump" from the single game-state stream trivial and reactively correct everywhere at once.
- Bloc's event/state ceremony is a better fit for apps with many discrete, complex business-logic transitions the *client* itself computes — but this app deliberately pushes almost all logic server-side (§12.1), so the client-side state layer is mostly "reflect Firestore, compute cheap derived UI booleans." Riverpod is lighter-weight for that shape of app and has excellent, low-friction Firestore stream integration.
- Plain `Provider` lacks Riverpod's compile-time safety and easy testability (mocking the Firestore stream provider for widget tests is straightforward with `ProviderScope` overrides), and Riverpod is its actively-maintained superset, so there's no real reason to pick the older package.

## 20. UX Specification

| Element | Behavior |
|---|---|
| **Player positions** | Local (You) always anchored bottom-center regardless of actual seat number; the other 3 players are rotated into left/top/right positions relative to you, computed from the seat offset — this is standard for card-table UIs and avoids a confusing "I'm always seat 3" fixed layout. |
| **Card animations** | Deal: cards animate flying from a central deck point to each hand (only your own hand shows face-up mid-flight; others animate face-down). Play: tapped card animates from hand position to its slot in the center trick area. Collection: on trick resolution, all 4 played cards animate sliding toward the winning player's team-side pile. |
| **Turn indicator** | A glow/highlight ring around the currently-active player's avatar/seat; a subtle pulsing border on your own hand area when it's your turn, plus (optionally) a haptic tick on mobile. |
| **Played-card placement** | Each of the 4 cards renders in a fixed compass-relative slot in the center (matching that player's seat position), not a generic stack — reinforces "who played what." |
| **Trump announcement** | A one-time animated banner/toast the moment trump is set ("♠ Spades is now Trump — set by [Player]"), plus a persistent small trump-suit badge visible for the rest of the game. |
| **Trick-winning animation** | Brief highlight/glow on the winning card + winning player before the collection animation runs. |
| **10-card collection indicator** | A row of 4 small ten-card icons in the team panel, greyed out until collected, then filled in with that team's color the instant collected. |
| **Victory animation** | Full-screen Court/Poopy Victory banner with team colors, confetti-style flourish, and the final 10-ownership + trump-team breakdown. |
| **Reconnection indicators** | A translucent "reconnecting..." overlay on a disconnected opponent's seat; a distinct banner if the *local* player is the one who dropped and is rejoining. |

Design goal: at any single glance, a player should be able to answer — whose turn is it, what's trump, who's winning which tens, and are all 4 players still connected — without opening any secondary screen.

## 21. Disconnect / Reconnect Policy (fills §3.2/§3.6/§17.5 gap)

**Assumption (new — the draft asks the question but doesn't specify numbers or the resulting flow; this spec makes it concrete):**

1. On disconnect (RTDB `onDisconnect` fires), the player's seat is marked `connected: false` and `status` moves `IN_PROGRESS → PAUSED`. No timer runs against `currentTurnSeat` while paused — the game simply waits, so a disconnecting player can never be penalized by running out a clock they can't see.
2. All 3 remaining clients show a "Waiting for [Player] to reconnect…" overlay; the game does not otherwise decay (hands, trick state, everything stays exactly as-is).
3. **Reconnect window:** If the player reconnects within, e.g., 5 minutes (tunable), `connected` flips back to `true`; if all 4 seats are now connected, `status` returns to `IN_PROGRESS` and play resumes exactly where it left off (their client simply re-subscribes and renders current Firestore state — nothing to "catch up" beyond a normal listener attach).
4. **Timeout exceeded:** If the disconnected player doesn't return within the window, the room is flagged `ABANDONED` (or, as a v2 enhancement, the remaining 3 players are offered a "forfeit the disconnected player's team" resolution) — v1 keeps this simple and just ends the game as abandoned/no-result, rather than inventing a forfeiture-scoring rule the draft never specified.
5. A player who intentionally backgrounds the app briefly (e.g., switches to another app for a few seconds) should **not** trigger this flow at all if they return before RTDB's disconnect grace period elapses (a few seconds, RTDB default) — this is naturally handled by RTDB's own connection-drop detection tolerance and requires no extra logic in this spec.

## 23. Assumptions Log (Consolidated)

For traceability, every place this spec filled a gap the draft left open:

1. Room codes: 6-char auto-generated by default, host may optionally supply a custom 4–10 char code (§3.1).
2. A "Ready" flag per seated player, in addition to "4 players present," gates game start (§3.4).
3. Host may optionally randomize seats pre-game (§3.4) — convenience only, not a rule requirement.
4. Trump establishment is instantaneous at the moment the card is played, not deferred to trick-end (§7.3) — resolves §11-D.
5. No 3-team-win-condition invented for the "no team gets all 4 tens after 13 tricks" case — declared a neutral Draw with the 10-split recorded (§10).
6. If trump is never established at all in a game, a ten-sweep defaults to a Poopy Victory (§10) rather than inventing a third victory category.
7. Disconnect/reconnect timing windows (5-minute reconnect grace, RTDB's native few-second drop tolerance) (§21) — the draft asks the question but specifies no numbers.
8. Riverpod chosen as the state-management library, with justification specific to this app's "mostly-server-driven" shape (§19.1).
9. "Court Victory" / "Poopy Victory" confirmed and flagged as house/custom terminology, not standard published Dehla Pakad terms (§1, §10).

Everything else in this document is a direct formalization of a rule already stated in the original draft, not a new invention.
